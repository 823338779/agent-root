# 三仓证据等级与冲突处理规范

## 目的

三仓分别表达实现、黑盒契约和用户体验。它们可能存在版本差异、规划先于实现、已知缺陷或过时文档。本规范确保复刻文档不会把期望、推断和现状混为一谈。

## 证据等级

| 标记 | 名称 | 定义 | 可以得出的结论 |
|------|------|------|---------------------|
| `I` | 已实现事实 | 当前源码、配置、数据库迁移或正式资源可静态确认 | 可以说明当前代码具备该结构或分支，但不能声称运行通过 |
| `A` | Active 测试契约 | active 自动化用例明确要求的行为 | 可以作为当前验收目标；本次未运行时必须注明 |
| `K` | Known Failure | 测试或缺陷台账明确记录的真实缺陷 | 必须写入当前限制和复刻防回归标准 |
| `P` | Planned Requirement | planned/disabled 用例或设计文档中的未来目标 | 只能写入规划或增强设计，不得写成当前能力 |
| `R` | Runtime Verified | 本次分析明确执行并观察到结果 | 只有用户授权运行验证后才可使用 |
| `F` | 强推断 | 多个调用方、DTO、Mock 或测试行为共同支持，但缺少对端源码或运行验证 | 必须说明推断依据和不确定边界 |
| `D` | 复刻建议 | 面向新工程的设计选择、改进或生产化补强 | 不代表 Nova 当前采用该设计 |
| `REQ` | 等价复刻要求 | 为保持已观察契约、安全边界或业务效果而提出的规范性要求；它不是证据等级 | 必须同时用 `I/A/K/P/R/F/D` 说明要求的依据，不得把 `REQ` 解读为当前已实现或已运行验证 |

`R` 专用于本轮实际执行并观察到的结果。文档中的 Requirement、复刻规则、验收要求和风险不得复用 `R`：前者使用 `REQ`（或在纯推荐设计中使用 `D`），风险使用 `K`。

## 冲突优先级

冲突不通过简单优先级覆盖，而是并列记录。处理步骤如下：
1. 确认三个仓库的版本和目标环境是否一致。
2. 分别记录实现事实、Active 期望和 UI 期望。
3. 若测试标记为 Known Failure，以“实现现状 \+ 期望行为 \+ 缺陷影响”表达。
4. 若只有 Planned 用例，放入“规划能力”，不得进入当前主链路。
5. 若实现中存在接口但无正式注册或入口，标记为“代码存在但产品不可用”。
6. 无法判定时保留冲突，不选择性隐藏证据。

## 外部依赖取证

没有对端源码时，从以下信息反向构建契约：
- 客户端方法、DTO、序列化字段和 Header。
- 配置项、URL 拼接、认证方式和超时。
- Tool 参数、Tool 结果和展示层消费。
- Mock、Fixture、错误断言和重试逻辑。
- 日志字段、异常翻译和用户可见文案。
- API、WS、UI 三通道对同一行为的期望。

文档必须分别给出：观察到的兼容契约、无法证明的内部行为、最小兼容对端、生产级推荐对端。

## 禁止事项
- 不用类名、方法名或文件路径代替业务解释。
- 不因存在测试就声称测试已通过。
- 不因存在源码分支就声称入口已开放。
- 不把历史设计文档直接当作当前实现。
- 不把推荐设计伪装成逆向得到的事实。
